# PRD Quality Review — prd-panda-2026-08-23

Reviewed against `prd-validation-checklist.md` (bmad-prd assets). Evidence drawn from `prd.md`; `addendum-prd.md` consulted for RD evidence-trail checks. Note: the Vision's reuse of the brief's manifesto phrasing ("Rent the agents. Own the environment.") was pre-declared intentional and is not treated as a defect.

## Overall verdict

**Decision-readiness: strong · Substance over theater: adequate · Strategic coherence: strong · Done-ness clarity: adequate · Scope honesty: strong · Downstream usability: adequate (leaning thin) · Shape fit: strong.** No CRITICAL findings — the PRD is safe to hand to architecture for the ~90% of surface it specifies precisely. It is *not yet* safe to hand to epics/stories unchanged: the primary success metric (SM-1) references four scenarios (S1–S4) that are never defined anywhere in the document, and two of the seven contracts declared in-scope for MVP (ToolProvider, SkillSource) have zero functional requirements. One focused revision pass closes all of this; the strategic spine, decision discipline, and testable-consequence culture are genuinely excellent and should not be touched in that pass.

### Findings (ordered by severity)

- **HIGH** — S1–S4 scenarios are referenced but never defined (§7 SM-1; dangling refs at §4.2 F2 "enables S1", §4.3 F3 "enables S3", §4.4 F4 "enables S2", §4.6 F6 "enables S4"). SM-1 is the **primary** release metric ("S1–S4 scenarios pass end-to-end") yet no section enumerates what S1–S4 are. They presumably live in the brief, but §0 promises the PRD itself states capabilities and testable behavior, and the rubric requires sections to stand alone. As written, SM-1 is unverifiable from this document and every "enables Sn" cross-ref fails to resolve. *Fix:* add a short "Scenario Index" subsection (e.g., under §7 or §3) defining S1–S4 in one line each (init-and-project / memory-transparency / drift-recovery / export-import portability, mapped to UJ-1..UJ-3), and keep the FR→S mappings.

- **HIGH** — ToolProvider and SkillSource are in MVP scope but have no functional requirements (§6.1 lists "seven Contracts (ExecutorAdapter, MemoryProvider, **ToolProvider**, ProjectionTarget, **SkillSource**, WorkspaceProvider, MethodPlugin definition)"; grep confirms ToolProvider appears nowhere outside §6.1 and SkillSource only in the Glossary §3 plus §6.1). Four of the seven contracts get full FR treatment with testable consequences; these two get none. An epic planner sourcing from §4 cannot write a single story for them, and §3's claim that "the seven v1 Contracts are named in §4" is factually false for these two. *Fix:* add minimal FRs — e.g., FR for ToolProvider (register/discover/invoke a Tool through the Kernel with typed result, consumer-suite parity like FR-15/16) and FR for SkillSource (supply Skills into the Registry with provenance, projected via FR-11..FR-13). Even thin spec-with-two-consequences beats silence, given both ship in v1.

- **MEDIUM** — FR-25 (`panda export` / `panda import`) has no Consequences block (§4.8). Every sibling CLI FR carries testable consequences (FR-24 exit codes, FR-26 remediation lines, FR-27 cache bound); FR-25 defers entirely to FR-21/FR-22 semantics without specifying command-level behavior. Inconsistent done-ness on the exact commands UJ-2 depends on. *Fix:* add consequences, e.g., non-zero exit + named cause when export encounters an unprojectable Registry entry; import into a non-empty panda home refuses without an explicit flag.

- **MEDIUM** — "Profile"/"Profiles" is load-bearing but undefined (used in §3 Registry definition, FR-21, §6.1). The Registry is "the canonical store of Tools, Skills, MCP servers, and Profiles" and Bundles contain "Profiles," but no Glossary entry says what a Profile *is* (an agent-scoped configuration bundle? a named preset?). Architecture will have to guess a domain noun. *Fix:* add a Glossary entry; if Profiles are only Registry-scope containers, say so in one sentence.

- **MEDIUM** — Security NFR clause is untestable as written (§10: "credential reuse modes unsafe per-environment are refused unless explicitly opted in (runcell pattern)"). Nothing defines what makes a mode "unsafe per-environment," so neither tests nor stories can verify refusal. Every other NFR in §10 has a bound or invariant; this one is an adjective wearing a noun's clothes. *Fix:* enumerate the refused modes concretely (e.g., same API key injected into two Executors' configs simultaneously unless `[ALLOW_SHARED_CREDENTIAL]` set), or name the runcell digest section that defines them.

- **LOW** — Assumptions Index roundtrip violated (§10 vs §9). §0 promises assumptions are "tagged inline `[ASSUMPTION]` and indexed in §9," but the token-efficiency budget's inline tag ("[ASSUMPTION: threshold validated during dogfooding]", §10) has no §9 entry. §9 indexes exactly three assumptions, all from §4.x. *Fix:* append the §10 entry to §9 (or move the inline tag into §12 budgets where it arguably belongs).

- **LOW** — JTBD entries that drive zero requirements (§2.1). "Social (teams)" and "Builder" jobs have no corresponding FR, UJ, or SM; SM-3 (external developer implements an adapter) gestures at the Builder job but no journey or feature work supports discoverability of contracts by outsiders. Mild persona-theater risk in an otherwise furniture-free document. *Fix:* either add one line acknowledging teams/external-devs are v1-non-goals served only opportunistically (§2.2 already hosts similar exclusions), or accept and note it — do not invent features.

- **LOW** — SM-2 gating timing ambiguous (§7). "30 consecutive days with zero hand-edited vendor configs" is a strong thesis-validating metric, but the PRD doesn't state whether the 30-day window must complete *before* v1 ships (release gate) or after (validation signal). These imply very different delivery schedules for epics. *Fix:* one sentence declaring which it is (RD-2 already uses "revisit condition: dogfooding" language, suggesting post-gate — make it explicit).

## Dimension judgments (brief)

- **Decision-readiness — strong.** §8 is exemplary: four decisions stated as decisions, each with rationale grounded in named evidence ([R1]–[R4] → addendum), what was *given up* named explicitly (semantic merge deferred, no hooks beyond the activation pair, no routing on quota), and even a revisit condition (RD-2 spawn-cost trigger). Trade-offs surfaced, not smoothed.
- **Substance over theater — adequate.** No persona pageant, no boilerplate NFRs (budgets in §12 are numeric and revisitable), counter-metrics are real design tensions (SM-C1/C2). Only residue is the undriven JTBD rows above.
- **Strategic coherence — strong.** Clear thesis (environment ownership > agent loyalty); every feature traces to it; MVP scope kind is coherent platform-scope with matching logic (contracts + proving implementations, not feature laundry).
- **Done-ness clarity — adequate.** FR-1..FR-28 almost uniformly carry verifiable consequences — genuinely rare and valuable. Gaps: FR-25 empty, security-NFR vagueness, and the two un-FR'd contracts.
- **Scope honesty — strong.** §5 Non-Goals does real work ("no kanban/task board of any kind"), §6.2 names deferred items with reasons, assumptions tagged. Density of open items is appropriately low because decisions were actually resolved with evidence, not rhetorically.
- **Downstream usability — adequate (leaning thin).** Glossary strong and mostly enforced; FR IDs contiguous and cross-resolving; UJs have a named protagonist carrying context inline. Dents: S1–S4 unresolved refs, missing ToolProvider/SkillSource/Profile glossary coverage, §3's "named in §4" claim false for two contracts.
- **Shape fit — strong.** Headless dev-tool correctly shaped as capability spec with light UJs; chain-top traceability (FR→S→SM→RD→addendum) matches the downstream BMAD workflow it declares in §0.
