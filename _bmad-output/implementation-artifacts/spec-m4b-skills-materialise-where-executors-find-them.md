## Intent

**Problem:** `skill` is a canonical registry entry kind that nothing materialises. `panda init` reports every skill as unprojectable for every target, so a skill registered once is available in no agent at all. It is also the gate on portability: an export bundle cannot carry what panda cannot put on disk, which is why ROADMAP-02 puts this before Epic 5.

**Approach:** the materialisation kind correction-01 C4 already anticipated — a projection target that writes a directory tree rather than merging text into one file, carrying the same guarantees: atomic, idempotent, foreign files untouched, per-target failure isolation. A skill entry is a POINTER (`entryPath`), so panda copies what the entry names; it does not author skills.

**Ownership becomes paths.** The ledger records owned TEXT inside a file, identified by hash. A directory tree cannot be owned that way, so this story extends the ledger's vocabulary to owned PATHS. That is not a detail: it is what makes removal safe.

**This is the first story in which panda DELETES from a user's filesystem.** Removing a skill from the registry must remove exactly what panda recorded writing and nothing else, and a skill directory a user made by hand must be invisible to that operation because it is not in the ledger. Everything else in this story is ordinary; this part is not, and it is where the review effort belongs.

**Verification is not optional here, and the acceptance criteria are already wrong in one place.** Story 2.9's criteria name `~/.claude/skills/<id>/SKILL.md`, `~/.codex/skills/<id>/SKILL.md`, and for OpenCode *"a directory plus its `skills.paths[]` entry"*. Measured before writing this spec: all three roots exist and are populated on this machine (38, 24 and 23 entries), a skill really is `<root>/<id>/SKILL.md` — and `opencode.json` has **no `skills` key at all** (`$schema`, `agent`, `default_agent`, `mcp`, `share`), so OpenCode discovers its root by convention and the config half of that criterion is an assumption from planning time. correction-01 exists because a previous build wrote panda's vocabulary at locations no executor reads. A location ships verified against the real tool or it does not ship.

## Boundaries & Constraints

**Always:** every materialisation location is verified by EXECUTION against the real tool — not "the directory exists" but "a skill panda put there is discovered by that executor"; removal removes only what the ledger records panda wrote, proven by a test in which a hand-made directory beside it survives untouched; writes are atomic and idempotent, and a second run with an unchanged registry changes no byte; foreign files and directories in a skills root are never touched, whatever they contain; per-target failure isolation holds — one executor's unusable root never stops the others; a skill whose `entryPath` cannot be read is reported and NOT partially materialised; a ledger that cannot be read is a refusal to remove anything, because removal without the record is guessing.

**Ask First:** materialising skills into a project scope rather than the machine scope; any transformation of a skill's content; inventing a skill format or a manifest panda authors; removing a tree the ledger claims but whose contents the user has since changed (that is drift on a tree, and the answer is a decision, not a default); reading skill content into the registry rather than pointing at it.

**Never:** no deletion of any path the ledger does not claim panda wrote; no invented location — an executor whose skills location panda has not verified reports its skills unprojectable, exactly as today; no partial tree left behind when materialisation fails; no touching of the developer's own skills roots by any test — those three directories hold real work.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Discovered, not just written | A skill panda materialised | The real executor finds and uses it | Unverified ⇒ not shipped |
| Materialisation | A registry skill entry | The tree appears at that executor's own location | Per-target coded error |
| Idempotence | Second run, same registry | Nothing written, no byte changed | N/A |
| Removal | A skill dropped from the registry | Exactly the recorded paths removed | Coded on failure |
| A hand-made skill | A directory the user created | Never touched, because the ledger does not claim it | N/A |
| Foreign files in the root | Unrelated files beside panda's | Untouched, byte for byte | N/A |
| Unreadable source | `entryPath` missing or unreadable | Reported; nothing partially written | Coded, isolated |
| Ledger unreadable | Corrupt ownership record | Refuses to remove anything; says so | Coded, not a crash |
| Per-target isolation | One root unusable | That target fails, the others materialise | Isolated |
| Drift on a tree | A materialised skill the user edited | Reported, not silently overwritten | Reported |
| The developer's own skills | Any test run | The three real roots are never touched | Proven |
| Unverified executor | An executor with no verified location | Reports skills unprojectable, invents nothing | N/A |

## Spec Change Log

- **The port grew a KIND, not a second engine (decision the frozen block left open).** `ProjectionTarget` is now a union: the historical config target (`filePath` + `merge`, unchanged, with an optional `kind: 'config'`) and `ProjectionMaterialiseTarget` (`rootPath` + `plan`). The split of labour inside the new kind is the load-bearing part: a materialisation target only DESCRIBES what the registry wants — which files, copied from which sources — and never touches the destination. Every write, every unlink and every ledger-versus-disk comparison happens once, in `packages/projection/src/materialise.ts`. MEASURED consequence of the alternative: had the target performed its own writes, `panda doctor`'s inspection mode would have needed a second code path to predict them, which is the exact divergence correction-01 was written to remove. `projectionTargetLocation(target)` gives both kinds one spelling of "where panda writes", so no caller can report a location the engine does not key ownership on.
- **Ownership as paths is an ADDITIVE field, not a ledger version bump (decision).** `ProjectionLedgerRecord` gained `ownedPaths?: {path, contentHash}[]`; `filePath` holds the root, `nativeLocation` the entry's root-relative directory, `contentHash` a hash over the whole tree. MEASURED: `PROJECTION_LEDGER_VERSION` is compared for exact equality and a mismatch makes the ledger `unreadable`, and an unreadable ledger both refuses every removal AND refuses to be rewritten. Bumping it would therefore have orphaned every claim on every machine that has run a previous build — panda would report its own MCP entries as foreign collisions forever. An optional field is compatible in both directions: an older build reads the record and simply claims no paths. A record WITHOUT `ownedPaths` can never authorise a removal, so the old shape is not merely tolerated, it is inert on the delete path.
- **Per-path hashes, not one tree hash (decision).** The tree hash alone would answer "has anything changed"; the delete path needs "is this exact file still the one panda wrote", because that is the predicate that runs immediately before `rm`. A malformed `ownedPaths` invalidates the WHOLE record and the record is dropped — under-claiming, which loses nothing recoverable, rather than handing the one operation that deletes a user's files an authority panda cannot vouch for.
- **`hashOwnedBytes` is deliberately not `hashOwnedText` (decision).** The config path normalises CRLF because a formatter rewriting line endings is not an edit a vendor can observe. A materialised file is COPIED from a source panda does not author, so "the same file" means the same bytes; normalising here would let panda overwrite — and, far worse, REMOVE — a file whose line endings a user changed on purpose.
- **All three skills roots verified BY EXECUTION; every one of them shipped (measurement).** Verified against the real binaries under an injected home, with panda doing the writing:
  - `claude-code` — `<home>/.claude/skills`. Claude Code has no offline listing, so `ANTHROPIC_BASE_URL` was pointed at a local stub and the request claude sends was captured: the planted skill appears in claude's own *"The following skills are available for use with the Skill tool"* block, which is PARSED rather than substring-matched. No credentials, no model call, no cost. **CORRECTED after review — "the redirect is total" was false, and so was "no network".** With `HOME`/`USERPROFILE` injected, claude keeps the developer's real skills out of the skills block (`graphify`, `ponytail` absent), which is the half this file asserts on — but the captured prompt still carries their real `~/.claude/CLAUDE.md`. And all three binaries still reach their vendors: attributed by PID, `claude` opens TLS to `api.anthropic.com`, `codex debug prompt-input` to `chatgpt.com`, `opencode debug skill` to `models.opencode.ai`. What the stub redirects is the INFERENCE endpoint — the Messages request is served locally and no billed model call happens — not the process's network access.
  - `codex` — `<home>/.codex/skills`. `codex debug prompt-input` renders the model-visible prompt and names the planted `SKILL.md` by absolute path.
  - `opencode` — `<home>/.config/opencode/skills`, PLURAL. `opencode debug skill` lists it with the exact `location` it loaded.
- **`skills.paths[]` stays out, and the measurement is recorded rather than the assumption (measurement).** `~/.config/opencode/opencode.json` on this machine has keys `$schema`, `agent`, `default_agent`, `mcp`, `share` — no `skills` key. OpenCode found the planted skill with that file untouched, so the root is convention and the epic's *"a directory plus its `skills.paths[]` entry"* was a planning-time assumption. Writing the key would have been panda inventing vocabulary at a location the vendor does not read.
- **OpenCode reads MORE than one root, which is why the differential matters (measurement).** Moving the root to `<home>/.opencode/skills` and to `<home>/.config/opencode/skill` (singular) both still PASSED: opencode genuinely scans all three. Only an unrelated location (`<home>/.local/share/opencode/skills`) turned it red — so the check can fail, and the root panda ships is one opencode really reads rather than the only one. The same mutation broke claude (`.claude/agent-skills`) and codex (`.config/codex/skills`) immediately.
- **`OPENCODE_DISABLE_EXTERNAL_SKILLS=1` in the live check (measurement, and a caveat worth stating).** Under a completely fresh injected home, `opencode debug skill` still listed 39 skills: 26 from the developer's real `~/.agents/skills` and 12 from the real `~/.claude/skills`. OpenCode honours the injected home for its own config root and for `~/.opencode`, and ignores it for those two external scans. Those are READS and the root snapshot proves nothing changed — but a location assertion could have passed on someone else's file, so opencode's own documented switch turns them off and leaves the injected root as the only source. **CORRECTED after review — "codex behaves similarly for one bundled `.system` skill" was wrong twice.** Re-measured with `CODEX_HOME` injected and cwd off the home: codex lists 32 skills, 5 from the injected home (its own `.system` bundle, which it MATERIALISES there) and **27 from the developer's real `~/.agents/skills`** — not from `~/.codex`, and not one. `~/.agents/skills` is read by two of the three, and is now covered by the root snapshot.
- **A skills entry is placed as `SKILL.md`, and a directory source is copied whole (decision).** `RegistryEntry.entryPath` is documented as the skill's ENTRY FILE; all three executors require the name `SKILL.md` exactly. So a file source is placed AS `<root>/<id>/SKILL.md` — panda renames the destination and never rewrites a byte of content. A directory source is copied entire, because a real skill keeps references beside its entry file and copying one of them materialises something that half works. A directory holding no `SKILL.md` anywhere is REPORTED, not written: a tree no executor discovers is the inertness correction-01 exists to prevent, and authoring the missing file would be panda writing skill content.
- **A registry id becomes a directory name, so it is validated as one (decision, SECURITY).** Ids are arbitrary non-empty strings and this is the first projection that turns one into a path. `../escaped` is reported with a reason and materialises nothing; the engine repeats the containment check on the resolved path and fails the target coded if a target ever plans outside its own root. Both halves were mutated: removing the id check leaves the engine's guard firing, which is the intended defence in depth.
- **A reason channel on the projection outcome (decision — closes a deferred entry).** `ProjectionResult.skipped` carries `{entryId, reason}` in the TARGET's own words. Story 2.7a's `reasonUnprojectable` derived every reason from the registry entry because ids were all the outcome carried; that was accurate while the only skippable shapes were "a kind no target projects" and "an mcp-server with no command", and it is wrong the moment a target has a reason of its own ("this skill names a source panda cannot read"). deferred-work.md named this story as the home; it is done.
- **Skills stop being reported unprojectable per EXECUTOR, not per target (decision).** `~/.claude.json` still cannot express a skill, and the config target still says so — but the sentence a user reads is about the executor, and for an executor with a verified root it is now false. So a config row drops skill ids wherever that executor materialises skills, and the skills row is the sole authority for them. Without this, `panda init` would report one skill as both written and impossible.
- **`InitResult.skills` / `Diagnosis.skills` are a separate array, not more `targets` rows (decision).** MEASURED: adding a second row per executor to `targets` broke five assertions across two pre-existing test files (`toHaveLength(2)`, three `toEqual` row lists, and a pinned key order). It is also the more honest shape — `TargetProjection.filePath` names a FILE in `targets` and a directory ROOT in `skills`, and a skills root is the one location where "projecting would change this" can mean panda removing something. Doctor's writability probe branches on it too: a config file is probed through its directory, because that is where the temp-file-then-rename lands, while a root is probed as itself and `permitsWrite` walks up to the nearest existing ancestor.
- **No project-scope skills, which is what exercises the unverified-location branch (decision).** Materialising into a project is Ask-First in the frozen Boundaries, so no profile declares a project-scope skills root and `panda project init` reports every skill unprojectable, exactly as before this story — the same refusal that keeps Codex out of a project's MCP configuration. That is not a hypothetical branch: it is the shipped behaviour of one of the two scopes, and it is pinned.
- **Removals are last and are not reversible; writes are (decision, with the ceiling named).** All of an entry's sources are read BEFORE the first byte lands, and each write records the bytes it displaced, so a failure halfway through a tree rolls back to exactly what was there. A failed removal after earlier ones is not undone: the target failed, so no ledger write happens, those entries stay claimed, and the next run finishes the job. Marked `ponytail:` with the upgrade path (a staging directory per target, which buys transactionality at the price of copying every tree twice).

  - `packages/projection/test/vendor-conformance.test.ts` — trait discovery. **CORRECTED after review: the first version of this edit made the check strictly WEAKER**, which is the one thing this round was told not to do. Filtering by shape meant a new `*_TRAITS` export without `mcpContainerKey` was silently excluded instead of failing loudly, and the mitigation the comment claimed ("skills traits are discovered the same way in `skills.test.ts`") did not exist. Discovery is TOTAL again: every `*_TRAITS` export is classified as either an MCP trait record or a skills trait record, and one that is neither turns the suite red whatever it is called. Both rogue shapes were mutated in and both fire.
  - `packages/projection/test/clause-suite.ts` and `test/drift.test.ts` — seven type ANNOTATIONS narrowed from `ProjectionTarget` to `ProjectionConfigTarget`. FORCED by the union: both files call `.merge()` on helpers that only ever construct config targets. No expectation added, removed or changed.

The real-roots snapshot was proven sensitive separately, against a fabricated home: it detects an addition, a deletion and an edit.

### Review round 2 — the delete path

The round's organising sentence was a reviewer's: *the containment and identity guarantees are enforced on the reversible half and assumed on the irreversible one.* Every entry below closes one of those assumptions, and each names the mutation that shows the guard firing.

- **The removal path had no containment at all (HIGH, USER-DATA).** `absolutePathOf()` re-checked `isUnderRoot` for every write; removals took the raw ledger string straight to `rm`. Reproduced by two reviewers independently, with an absolute path (`~/.claude.json` and a sibling `id_rsa` both deleted) and with a RELATIVE one, which resolves against the process working directory. A ledger record is a file panda PARSED, so its paths are input, not fact. Now every claimed path is resolved and containment-checked when the authority set is built AND again next to the syscall; a record naming anything outside the root is reported as `foreign-collision` and KEPT, never acted on. My own change log had asserted this was already true ("the engine repeats the containment check on the resolved path") — it was true of writes only, and that sentence is corrected above.
- **A junction voided the entire `rmdir` argument, with no tampering required (HIGH, USER-DATA).** Measured mechanically: `rmdir` on a junction to a NON-EMPTY directory removes the link without consulting the target. And a hash check reads THROUGH a link, so the realistic sequence — panda materialises a skill, the user later moves that tree into their own repository and leaves a junction behind — read as `intact`, authorised removal, and deleted the real file outside the root, silently. The story's central safety sentence ("`rmdir` refuses a directory that still holds anything, so a foreign file keeps its directory alive without panda having to notice") was therefore void through a reparse point. Fixed with `lstat` along the WHOLE path below the root, not just the final component: `lstat` refuses to follow only the last one, so checking the file alone would have missed the junction-at-`<id>` case, which is the one that matters. A link at any depth disqualifies the record from removal, and the prune walk stops at one before `rmdir` is reached.
- **Two ids, one path (HIGH, USER-DATA).** Ownership keyed on `entryId` and nothing compared PATHS. `alpha` and `Alpha` are one directory on Windows; with both registered and one dropped, panda deleted the survivor's file with `drift: []`, and the next run reported `removed-by-user` and locked it out forever. Fixed by applying the removal list against the FINAL record set: a path any surviving record still claims is never removed, and the collision is reported instead of being silent. This is the general "two records, one path" hole, not a case-sensitivity special case.
- **A record that failed to qualify as authority was ERASED (HIGH, USER-DATA).** The `record === undefined` branch reported a foreign collision and continued without keeping the record, and the engine then persisted the reduced set — so a tree became a foreign collision forever, and in the `ownedPaths`-absent case with no warning at all. That falsifies the load-bearing sentence of the compatibility decision above ("under-claiming, which loses nothing recoverable") and is exactly what Story 2.8's review declared terminal for the whole-ledger case: *under-claiming on READ is recoverable; PERSISTING that under-claim is terminal.* Now EVERY claimed record this run does not consume is carried through untouched.
- **Two predicates, because one decision was serving two questions (MEDIUM, and the fix is a second hash).** Byte-exactness is right for removal — a false match precedes `rm`. For the OVERWRITE decision it reintroduced precisely what Story 2.8 fixed on the config path: `core.autocrlf` on a skills root kept in a dotfiles repository flips every materialised `SKILL.md`, every panda skill goes permanently `edited`, and the product has no adopt, force or reclaim path out of it — deleting the directory does not reset it either (`removed-by-user`, claim kept, never re-added). `ProjectionOwnedPath` gained an optional `canonicalHash`; removal compares raw bytes, the overwrite verdict compares normalised text, and the per-file write decision stays byte-exact so a CRLF-flipped file is quietly repaired rather than condemned. My own sentence contained the distinction and then discarded it.
- **Four guards the design rested on were not falsifiable (MEDIUM).** Both delete-path reviewers mutated them independently and got fully green: `hashOwnedBytes` normalising EOL (including the predicate that runs immediately before `rm`), `isLedgerRecord` tolerating a malformed `ownedPaths` (the only thing between a hand-edited ledger and `readFile(123)`, which in node reads a FILE DESCRIPTOR), the `ownedPaths !== undefined` authority filter (the clause that justifies not bumping the ledger version), and the engine's write-path `isUnderRoot`. All four now have a case, and all four fire. The last one needed a hand-rolled target to reach: the skills target's own id check makes it unreachable through the shipped path, which is exactly why it was a guard nobody could show firing.
- **Two failure shapes failed the whole target forever instead of reporting one entry (MEDIUM).** A claimed file that became a directory (`EISDIR`) or one the user denied read on (`EPERM`) escaped `readIfPresent`, which swallowed only `ENOENT`; and a dot-only id hit the engine's containment guard as a THROWN failure. Either one unmaterialised every other skill for that executor. `readIfPresent` now answers `unreadable` — present, and not what panda wrote, which is drift on one entry — and `isSafeSegment` rejects dot-only ids per entry.
- **An off-union target killed the whole run (MEDIUM).** The ownership scope was computed outside the per-target `try`, so a target that is neither kind threw out of `runProjection` and took every sibling with it — against the engine's own documented containment. Pre-existing in shape, widened by this story from "a non-string `filePath`" to "any target off the union" on a published port. Everything derived from the target now lives inside the try.
- **The codex discovery proof measured the CWD, not the home (HIGH).** It ran `codex debug prompt-input` with `cwd === homeDir` and DELETED `CODEX_HOME`, the only knob that moves codex's home on Windows — so it verified PROJECT scope, the one scope this story explicitly refuses to ship, and left the shipped branch unmeasured. The location was right; the proof was not, and correction-01's rule is verified-or-not-shipped. `CODEX_HOME` is now injected and every case runs from a sibling directory that holds no configuration, so home scope and project scope are no longer the same string for any of the three. Mutation: delete `CODEX_HOME` and the codex case goes red against the developer's real `~/.codex`.
- **Claude's case passed on a corrupt skill (HIGH).** With the frontmatter deleted from `SKILL.md`, codex and opencode went red and claude stayed green, because claude falls back to the DIRECTORY name and the assertion was a bare token in a 200 KB body. The skills block is now parsed and membership is asserted on name AND description, where the description carries a marker that exists only in the file panda copied. Re-mutated: all three go red.
- **The chain from "the binary confirmed this location" to "this is where panda writes" was broken (HIGH).** The live check measures each trait record's `defaultRoot`; production writes at `profile.machineSkills(homeDir)`. Two different strings, and mutating the production one to a bogus root left the live suite fully green. Worse, `executors.ts` claimed an assertion tying them ("asserted against the shipped traits in `test/executors.test.ts`") that `rg` could not find. `skills.test.ts` now asserts the equality directly, and the comment names the file that really does it.
- **The honesty line was invisible under the reporter CI runs (HIGH).** `pnpm test` runs vitest with no `--reporter`, and the default one swallows `console.log` from a passing test — so on `ubuntu-latest`, where none of the three binaries exists, the suite was green, silent, and had measured nothing while `measured + notMeasured === 3` was satisfied by `0 + 3`. Now written with `process.stdout.write`; verified visible with `PANDA_LIVE_SKILLS=0`.
- **OpenCode reads four roots and panda writes into the one that loses (MEDIUM, recorded and surfaced).** Verified independently by planting the same id in all four: `~/.config/opencode/skills`, `~/.config/opencode/skill`, `~/.opencode/skills` and `~/.opencode/skill` are all scanned, and `~/.opencode/skills` silently wins while `init` and `doctor` report panda's own write as done. Only an unrelated location (`~/.local/share/opencode/skills`) turns the live case red, so the check is not vacuous. Stated where a user sees it, in `packages/projection/README.md`, alongside the fact that claude names a skill by its DIRECTORY while codex and opencode name it by the source's frontmatter — so a registry id that differs from the frontmatter shows up under two different names.
- **`doctor` was still describing a file (MEDIUM).** The `out-of-date` resolution said "projecting rewrites this file" for a directory root and carried a caveat about a read-only file attribute. It now says what projecting a root can mean, REMOVAL included. The related granularity loss — a skills target that fails outright leaves its entry ids named by neither row — is stated where `reasonUnprojectable` is decided rather than papered over: the alternative is a config row asserting the executor has no representation for a skill, which is false for one that merely could not be written to.

## Design Notes

**Why removal is the whole story.** Everything else here is a write, and panda has done writes carefully since 2.8. This is the first delete. The ledger is the only thing standing between "remove the skill panda installed" and "remove the directory that happened to have that name".

**Why `skills.paths[]` is not in the criteria above.** It was in the epic's, and it is not in OpenCode's config. Building it would be inventing vocabulary at a location the vendor does not read — the exact failure correction-01 was written for.

**Deliberately not built.** No project-scope skills, no content transformation, no authored manifests, no bundle export.
